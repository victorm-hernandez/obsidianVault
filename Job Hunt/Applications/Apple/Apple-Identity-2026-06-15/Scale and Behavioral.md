### System Design & Scaling the Current Architecture

1. **Horizontal Scaling:** You mentioned using a "Forecast Generator" to pre-generate forecasts using a shared buffered channel. How does this architecture scale if we need to deploy 10 instances of your application behind a load balancer?
	1. Despite being stateful the application is capable to scaling horizontally with hard limits imposed by the throttling and load that the third party APIs can take, to properly scale this horizontally we would need to refactor the cache out of the web servers and into a distributed cache as to avoid redundant requests to the third party APIs. An a hybrid approach may bring the best of both worlds, if we are ok with having a fixed set of locations for a long time, large enough to provide the required "randomness", we can then create a distributed cache, but avoid introducing it in our main flow, by having a local copy of this cache that will be continuously updated in the background by a routines. 

2. **Distributed Caching:** Your custom thread-safe circular log cache lives in memory. If we scale out horizontally, each node will have its own cold cache. How does this impact our cache hit rates and the downstream API rate limits, and what architecture would you move to?
	1. As per my last answer, the right move would be to move from a local cache to a distributed cache approach and maintain the list of random locations in a shared location. This change would require not only refactoring the cache but potentially refactoring the generation responsability to a different role which would scale independently of the cache and the web servers a generator role with a pool of workers.

3. **Thundering Herd:** The third-party NWS API has strict throttling limits. If we suddenly get 10,000 requests per second right at startup (before the cache is populated), how does your service prevent overwhelming the downstream APIs?
	1. The current design of the API decouples the requests from the generation of the forecast, the number of RPS that our API receives is orthogonal to the load that we put on the third party API which is constant and throttled internally. 

4. **Data Staleness vs. Availability:** You chose a 10-minute expiration for cached data to prevent serving stale info. If the NWS API goes down for an hour during a major weather event, how does your system behave, and how would you handle this at a massive scale?
	1. I would like to mention that the expiration time of the cache is a an error on the design, since after further inspection I found that the NWS APIs have proper expiration HTTP headers as part of the response and that I should use those instead of the arbitrary value, the NWS expiration is much more flexible, few hours instead of few minutes.
	2. While this provides a better safety net, it still doesnt make our service resilient to long periods of downtime on the third party APIs. There are few options to further improve our resiliency:
		1. First option being having an alternate data source in case the first one is down, this would require another weather service that can be used in the first one is down. This is introduces additional cost and potentially complexity since we now need to introduce an maintain the required machinery to handle both of the services.
		2. Another option, as long as the use case and the business allows it, would be to serve stale data, even if the data is expired it may still be of use in some scenarios. For instance if this is used as test data for a specific test bed/framework. Having stale data is irrelevant, however if this is used for event planning or any scenario where the data needs to be fresh the first path is the right one.
		   
5. **Memory Constraints:** Can you walk me through the memory implications of your Forecast Generator? What happens if the consumers (API handlers) are slower than the producer under heavy concurrent load? Could this lead to an Out Of Memory (OOM) panic?
	1. The generation is isolated from the consumption patterns of the application, it has a fixed set of workers and a fixed throttling for outgoing request. Memory wise, the amount of memory used by the generation is also fixed, the two biggest components memory wise is a buffered channel used to synchronize the workers and a circular log of fixed size used to serve data from memory. These two will remain the same size regardless of the load.
	2. The main concern with very heavy load is the exhaustion of file descriptors and the memory used for each of the requests

6. **Rate Limiting at Scale:** You noted in your README that you want to throttle incoming requests to avoid abuse. If you are running multiple instances of this service globally, how do you implement distributed rate limiting?

	1. An option is to keep the request fingerprints and the related request counts on a distributed cache, this would allow for immediate detection of noisy clients. The trade off that we will introduce a lookup to the cache that while it should be small if the services are collocated, it still adds up in the big picture. Another trade off is that the cache system itself can become a bottleneck or point of failure, requiring redundancy and fallback strategies.
		1. This is the industry standard. There are few algorithms for this purpose. 
			1. **Fixed window,** keep a simple counter with an expiration per fingerprint, the expiration defines the time window. Trade-off, the distribution of the spike can be focus on the end and the beginning of a window, allowing practically twice the max number of requests.
			2. **Sliding window**, keep a sorted list of requests with the time per fingerprint, you can remove the oldest members and count how many requests happened in a time window. The main tradeoff with this being that for devices that have a large number of request will heavily increase the amount of memory required to keep that data around.
			3. Leaky bucket. Use a refill rate based on the last time a request happen, reduce the available bucket every time a request happens. This needs to happen in a lua script on redis to avoid race condition from concurrent go routines.
		2. There are few options for the architecture of our system using a distributed cache for rate limiting.
			1. If the eventual consistency for this data is not option, for instance expensive API calls billing. The proper pattern requires blocking the requests pending a read on the distributed cache. The trade off is that it introduces additional latency and a new bottleneck and point of failure.
			2. If eventual consistency is acceptable, for instance using this as a denial of service protection or service abuse protection, a slightly delay in the throttling is acceptable, in which case, having a local copy of the throttling shared cache data and update it periodically would be the right solution since it does not introduce latency on the main flow and still achieves the same results.

8. **Circuit Breakers in Distributed Systems:** You mentioned adding a circuit breaker as a next step. In a multi-node deployment, would you implement the circuit breaker state locally on each node or globally (e.g., via Redis), and what are the trade-offs of your choice?
	1. My current plan for a multi node deployment decouples the generator role from the web server role. In this plan the web server will scale out completely independent from the generator role, which will most likely remain pretty small given the throttling thresholds of the NWS APIs, a single node can maintain the state and additional nodes would be available only as backups , hence there is no need to share data across generator nodes since there will be only a single node active at any given time.
	2. In the hypothetical scenario that multiple generators are ever required, still in this scenario sharing state for resiliency purposes while instinctively makes sense, in practice introduces unnecessary complexity. The impact of having distributed boxes with independent circuit breakers is a fixed number of additional requests to an API which in most cases is acceptable. Let's go over potential solutions and why they not help us significantly.
		1. Using a distributed cache introduces latency from the additional network request, introduces a new point of failure and potential bottleneck as well.
		2. Using gossip in this instance, also introduces complexity to our system while still having a delay that may potentially compare with the delay local circuit breakers may have before opening the circuit.
   
9. **Handling Slow Consumers:** How does your service currently handle long-standing, slow connections from clients (e.g., clients on a 3G network)? How does this impact your concurrent request capacity in Go?
	1. Slow consumers may hog TCP connections to the point where our server is out of file descriptors or memory to handle it. There are multiple options on this regard:
		1. Respond with an HTTP 429 Too many requests after a threshold of active requests in the server blocking any new calls to give time for the slow clients to complete.
		2. We define a ceiling of the time we are willing to wait for a slow client by creating timeouts for the different stages of the TCP connection as part of the web server (read headers, read request, iddle connection). If this ceiling is reached we simply close the connection. This also acts as a last resort protection in case of a denial of service attack by using an artificially slow large number of clients with the intent of exhausting our service file descriptors. 
		3. This problem however is better suited for a load balancer/api gateway.
