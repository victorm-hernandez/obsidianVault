### Certificate Architecture & Trust Models

The hierarchical structure that allows endpoints to verify identities without talking to a centralized database every time.

- **Root CA (Certificate Authority):** The cryptographic anchor of the entire PKI. The Root CA issues certificates to Intermediate CAs and is kept entirely offline to prevent compromise.
    
- **Intermediate CA (Subordinate CA):** The operational authority that actively issues end-entity certificates. If compromised, an Intermediate CA can be revoked by the Root CA without destroying the entire PKI.
    
- **Chain of Trust (Certificate Path):** The sequence of certificates starting from the end-entity, routing through one or more Intermediate CAs, and ending at a trusted Root CA.
    
- **Cross-Certification:** A process where two independent Root CAs sign each other's certificates, allowing clients from PKI "A" to trust endpoints in PKI "B" without sharing a common root.

### Certificate Revocation List (CRL)

A CRL is a time-stamped, CA-signed file containing a list of serial numbers for all unexpired certificates that have been revoked.

- **The Mechanism:** The client downloads this file periodically (e.g., every 24 hours) and caches it locally. During a TLS handshake, the client checks if the server's certificate serial number is on this list.
    
- **The Architectural Challenge:** CRLs suffer from severe scalability limitations. As more certificates are revoked, the file grows linearly, consuming significant bandwidth and memory on the client side. Furthermore, the periodic polling nature introduces a dangerous vulnerability window—if a certificate is revoked minutes after a client downloads the CRL, the client will incorrectly trust the compromised certificate until the next scheduled update.

### Online Certificate Status Protocol (OCSP)

OCSP replaces the batch-download model of CRLs with a real-time, targeted network request.

- **The Mechanism:** Instead of downloading a comprehensive list, the client sends an HTTP request to an OCSP Responder (operated by the CA) querying the status of a specific certificate serial number. The responder replies with a signed `Good`, `Revoked`, or `Unknown` status.
- **The Architectural Challenge:** While OCSP mitigates the bandwidth and synchronization latency problems of CRLs, it introduces two distinct infrastructure issues. First, it creates a privacy leak: the CA learns exactly which services a client is attempting to access. Second, it introduces a hard dependency on the CA's uptime. If the OCSP responder is unreachable, the client must either hard-fail (breaking service availability) or soft-fail (allowing a potentially revoked certificate through).
- **The Modern Solution:** **OCSP Stapling** (TLS Certificate Status Request) resolves both issues. The infrastructure hosting the certificate queries the OCSP responder itself, caches the time-stamped response, and "staples" it to the certificate payload during the initial TLS handshake. This eliminates the extra network hop for the client, preserves privacy, and decouples the immediate handshake from the CA's real-time availability.



**CSR (Certificate Signing Request):** A base64-encoded block of text generated by the client containing its public key and identifying information. The CA signs the CSR to generate the final certificate.


**RSA vs. ECC (Elliptic Curve Cryptography):** RSA relies on prime factorization, requiring large key sizes (e.g., 2048-bit) for security. ECC relies on algebraic curves, offering the same security with much smaller key sizes (e.g., 256-bit), drastically reducing TLS handshake latency.

**HSM (Hardware Security Module):** A dedicated, tamper-resistant physical computing device used to generate, store, and manage cryptographic keys. Root CAs always have their private keys generated and locked inside an HSM.

**TPM (Trusted Platform Module):** A secure crypto-processor embedded on a device's motherboard. Used for endpoint security to ensure private keys cannot be exported or copied off the device.
