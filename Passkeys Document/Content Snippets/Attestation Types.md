In Web Authentication (WebAuthn), **attestation** is the mechanism by which an authenticator cryptographically proves its provenance (its make, model, and physical characteristics) to the Relying Party (the web server).

When a user registers a new credential, the server can request an attestation statement. Depending on the type of authenticator (e.g., a hardware security key, a Windows PC, an iPhone), the format of this proof changes.

Here is a breakdown of the different attestation types defined in the WebAuthn specification, what makes them unique, and their typical use cases:

### 1. None (`none`)

- **What it is**: The authenticator provides no attestation data whatsoever. It simply returns the new public key.
- **What makes it different**: There is zero proof of the authenticator's hardware or software characteristics. The server has to trust that the public key is secure without verifying the device that created it.
- **Use Case**: **Consumer Web Applications**. For most websites (e.g., social media, e-commerce), the server only cares that the user has _some_ secure credential that can be used later; it doesn't care if it's a YubiKey, a MacBook, or a software password manager. Requesting `none` preserves user privacy and prevents device fingerprinting.

### 2. Packed (`packed`)

- **What it is**: A generalized, highly optimized attestation format designed specifically for WebAuthn.
- **What makes it different**: It is very compact. It comes in two flavors:
    - **Basic**: Contains an X.509 certificate chain linking back to the manufacturer, proving the exact make/model.
    - **Self**: Doesn't contain a certificate; the authenticator just uses the newly created credential private key to sign the attestation data.
- **Use Case**: **Modern Security Keys and Enterprise Auth**. Basic packed attestation is used by modern FIDO2 hardware keys (like YubiKeys). A bank or enterprise might use this to enforce a policy that says, _"Employees can only log in using specific, company-approved hardware keys."_ Self attestation is used when the server wants cryptographic proof that the private key genuinely controls the response, but doesn't need manufacturer verification.

### 3. TPM (`tpm`)

- **What it is**: Attestation generated by a Trusted Platform Module (TPM) chip.
- **What makes it different**: It uses specialized, highly complex data structures defined by the Trusted Computing Group (TCG) rather than standard WebAuthn formats. It relies on the Endorsement Key (EK) baked into the motherboard's TPM during manufacturing.
- **Use Case**: **Windows PCs in Enterprise**. When you use Windows Hello (PIN or biometrics) as a platform authenticator, Windows uses the PC's TPM. Enterprises use this attestation to cryptographically verify that an employee's credential is safely locked inside the un-exportable hardware of a corporate laptop.

### 4. Android Key (`android-key`)

- **What it is**: Attestation generated by the Android Keystore system.
- **What makes it different**: The attestation certificate is issued by Google. It contains special Android-specific extension data, including the OS version, patch level, and whether the key is stored in the hardware Trusted Execution Environment (TEE) or Secure Element (SE).
- **Use Case**: **Android Platform Authenticators**. Used when a server wants to verify that an Android phone is acting as the authenticator and wants to guarantee that the key is physically bound to the device's secure hardware, rather than just being a software key.

### 5. Android SafetyNet (`android-safetynet`)

- **What it is**: Attestation based on Google's SafetyNet API (which evaluates device health).
- **What makes it different**: While `android-key` proves where the key is stored, SafetyNet proves the overall health of the operating system. It provides an assertion that the device is not rooted, infected with malware, or running a compromised OS. _(Note: Google is deprecating SafetyNet in favor of the Play Integrity API, but this format remains in the WebAuthn spec for legacy support)._
- **Use Case**: **High-Security Mobile Scenarios**. Used by financial institutions or high-security applications that want to refuse registration if the user's Android phone is rooted or running a custom, potentially insecure ROM.

### 6. Apple Anonymous (`apple-anonymous`)

- **What it is**: Apple's proprietary attestation format for iOS and macOS devices.
- **What makes it different**: It is specifically designed to preserve privacy. Apple issues the attestation certificate, but it deliberately obscures the exact device model (e.g., you can't tell if it's an iPhone 13 or an iPhone 15) and OS version.
- **Use Case**: **Apple Platform Authenticators (Face ID / Touch ID)**. It allows Relying Parties to verify that the credential is fundamentally backed by Apple's Secure Enclave hardware, providing high security assurance without allowing the server to track or fingerprint the user's specific device.

### 7. FIDO U2F (`fido-u2f`)

- **What it is**: A legacy format.
- **What makes it different**: It uses older ASN.1 data structures that were defined for the original FIDO U2F protocol, which predates the modern WebAuthn standard.
- **Use Case**: **Backwards Compatibility**. When a user tries to register an older hardware key (manufactured before FIDO2/WebAuthn existed), the browser wraps the old U2F response in this format so the modern server can still parse and accept it.

### 8. Compound (`compound`)

- **What it is**: A meta-format.
- **What makes it different**: It doesn't define a new attestation type itself; instead, it acts as an envelope that can contain _multiple_ attestation statements of the types listed above.
- **Use Case**: **Complex Trust Scenarios**. Used in rare, highly specific scenarios where a single credential might be backed by multiple roots of trust simultaneously (e.g., proving both hardware storage via TPM _and_ passing an OS-level health check), requiring the server to evaluate multiple proofs together.
